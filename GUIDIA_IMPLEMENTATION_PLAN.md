# Guidia — Implementation Plan

This plan maps the current repository (see `GUIDIA_CURRENT_ARCHITECTURE.md`) to the product described in `README.md`. It supersedes the README's own condensed 10-phase roadmap with the 20-phase breakdown used for execution tracking. Phases are ordered by dependency; later phases assume earlier ones are complete. Work proceeds phase-by-phase without stopping for confirmation between phases, per project direction — this document is what "reasonable engineering decisions" are checked against.

Chosen stack decisions (made from the audit, not asked as open questions, because the repository already implies them):
- **Backend**: replace the disconnected FastAPI stub with a proper Node/Express (or FastAPI, expanded) service — a JS backend keeps one language across the stack and simplifies the AI Gateway; final call recorded in Phase 1.
- **Database**: SQLite for development via an ORM with a clean migration path to Postgres in production (Prisma or SQLAlchemy depending on backend language choice).
- **AI provider**: Google Gemini, kept behind a provider-agnostic AI Gateway (`AI_PROVIDER`, `GEMINI_MODEL`, `GEMINI_API_KEY` env vars per README), called **only from the backend**, never the browser.
- **Naming**: standardize on "Guidia" everywhere; remove all "Guideia" references.

## Phase 2 — Authentication
**Dependencies:** Phase 1
**Status: complete, including forgot/reset password and a real "Remember me."** `Auth.jsx`'s hardcoded-OTP flow was replaced by `pages/auth/Login.jsx` and `Register.jsx` early this project; this pass added `ForgotPassword.jsx` and `ResetPassword.jsx`, a new `PasswordResetToken` table, and `POST /api/auth/forgot-password` / `POST /api/auth/reset-password`.

**Route map** (implemented, not just planned):
```
/  → /login ⇄ /register → /onboarding → /app/home
              ↓                              ↓
      /forgot-password              /app/{learn,practice,assistant,safety,
              ↓                      memory,progress,guardian,notifications,
      /reset-password                settings}
                                            ↓
                                        /admin (role=ADMIN only)
```
Every `/app/*` path and `/admin` is gated by `ProtectedRoute` (redirects to `/login`, preserving the attempted destination via router state — `location.state.from`, not a `?redirect=` query param, so the intended path is never exposed in the URL/browser history/referrer headers, which is a stricter privacy bar than the original plan called for). `/admin` additionally requires `role="ADMIN"`.

**Forgot/Reset Password — real, not decorative:** `requestPasswordReset` always returns the same generic response whether or not the email exists (verified: identical response body/timing-insensitive for a real vs. fabricated address) — no account-enumeration leak. Since no email provider is configured in this deployment, the reset link is logged server-side only, explicitly marked `[DEV ONLY — no email provider configured]` in both the log line and a code comment — the UI never claims an email was sent when it wasn't. Verified live: mismatched passwords rejected, invalid/expired/reused tokens rejected, a successful reset revokes every existing session for that account (forces re-login everywhere) and the old password stops working immediately.

**Remember Me is now real**, not a decorative checkbox: unchecked → a 1-day refresh cookie; checked → the standard 30-day cookie. Verified via `Set-Cookie` header inspection that the `Max-Age` actually differs (86400 vs 2592000).

**Password UX:** both Register and Reset Password show a live, neutral→success requirements checklist (`PasswordRequirements`/`passwordRules.js`) and a live "Passwords match"/"do not match" indicator — never a jarring red state while still typing. A shared `PasswordInput` component adds a visibility toggle with a real accessible label ("Show password"/"Hide password"), used on Login, Register, and Reset Password.

**Login page** rebuilt to the two-column brand-panel layout (calm product messaging on the left, form on the right, panel hidden below 900px in favor of a compact inline logo) rather than a single centered card.

**Already correct before this pass, verified again here:** logout revokes the server-side session (confirmed a `refresh` call fails with `SESSION_EXPIRED` immediately after logout, not just client-state clearing) and the browser-back-after-logout case is handled by architecture, not a special case — `ProtectedRoute` re-evaluates `AuthContext`'s live `status` on every render, so a popstate/back navigation to a protected path re-runs the guard against current (now-guest) state rather than restoring a cached authenticated view.
**Testing:** duplicate email, invalid email, weak password (client + server), wrong credentials, expired/revoked session, logout, protected-route redirect-with-preserved-destination, role-gated route, forgot-password (existing + nonexistent email), reset-password (mismatch, invalid token, valid reset, old password rejected, token single-use enforced), remember-me cookie duration — all tested against the live backend, not just written and assumed.
**Completion criteria:** met.

## Phase 3 — Design System and UI Reconstruction
**Dependencies:** Phase 1
**Status: re-scoped from "full visual rebuild" to "fix what was actually broken, start the reusable component layer."** On inspection, `index.css` already had a real, fairly coherent token system (color/spacing/radius/shadow/typography custom properties, consistently used across every component via `var(--x)`) — the audit's original "needs a design system" framing undersold what was there. What genuinely needed fixing:
- **Dark mode was completely non-functional** — `darkMode` was a real, persisted preference (toggle in Settings, saved to the database) that nothing in the CSS or component tree ever read. Added a full `[data-theme="dark"]` token override block (remapped surfaces/text/borders/light-tint variants for contrast on a dark background, not just inverted) and wired `AppStateContext` to set `document.documentElement.dataset.theme` reactively — now genuinely functional, not just a UI element that looked like a setting.
- **Reduced Motion was the same story** — tracked and persisted, never applied. Added a real `[data-reduced-motion="true"]` override (plus honoring the OS-level `prefers-reduced-motion` regardless of the in-app toggle) that collapses all animation/transition durations.
- Fixed a real dead/broken CSS rule: `[data-mode=scared] :root{--success-light:...}` is invalid — `:root` never matches as a descendant of anything, so this rule silently did nothing. Removed it along with several duplicate rule blocks (`.otp-wrap`/`.otp-box`, `.btn-danger`/`.btn-warn`/`.btn-teal` base declarations, `.flex-col`/`.w-full`/`.text-center`/`.justify-center`) that were defined twice in the file.
- Fixed genuinely fake content found while touching this area: `SettingsPage.jsx`'s "Family Guardian" row hardcoded "Guardian: Son (Dhaka) — Online — approves transactions" regardless of whether the signed-in user had any guardian relationship at all — replaced with a real link into the (now real, Phase 12) Guardian dashboard.
- Started the reusable component layer: `src/components/ui/GuidiaLoadingState.jsx`, `GuidiaEmptyState.jsx`, `GuidiaErrorState.jsx`, `GuidiaButton.jsx`, `GuidiaCard.jsx` — thin wrappers around the existing CSS classes. `GuidiaLoadingState` replaced the identical loading-spinner markup that had been copy-pasted across `GuardianDashboard.jsx`, `MemoryBook.jsx`, and `ProgressDashboard.jsx` this session — real adoption, not an unused component sitting alongside the old pattern.
**Deliberately not done:** `fontSize` (the text-size accessibility setting) is only partially wired — it now scales base/inherited text via a CSS variable, but most headings and labels in this codebase hardcode their own px `font-size` in inline styles and won't rescale; a full fix means migrating those to rem, which is a large mechanical change across every component, not attempted here. No page-by-page visual rebuild, no `GuidiaModal`/`GuidiaProgress`/`GuidiaInput`, no `Sidebar`/`TopBar` rewrite, no systematic emoji sweep, no Bootstrap grid adoption — the existing CSS grid/flex utilities already serve that role and introducing Bootstrap alongside them would add a second, conflicting layout system rather than fix anything.
**Completion criteria:** met for "tokens exist and are consistent" (they already did) and for "every persisted preference has a real effect" (dark mode, reduced motion now do; font size partially does, documented). Not met for full component-library coverage or a systematic visual redesign.

## Phase 7 — AI Core
**Dependencies:** Phase 1
**Status: gateway implemented; one real feature wired end-to-end on the backend.** `backend/src/ai/gateway.js` is the single module allowed to import an AI SDK — `generateText()` and `analyzeImage()`, both routed through `env.aiProvider`/`env.geminiModel`/`env.geminiApiKey` (never a `VITE_`-prefixed var, so it can never reach the browser bundle — verified by grepping the built `dist/` output). `isAvailable()` lets callers degrade gracefully instead of throwing when no key is configured.
Built on top of it: `backend/src/services/assistantService.js` + `controllers/assistantController.js` + `routes/assistantRoutes.js`, exposing `GET /api/assistant/status` and `POST /api/assistant/message` (authenticated, rate-limited, zod-validated, cognitive-state- and language-aware system prompt). Verified live: `status` correctly reports `unavailable` with no key configured, `message` returns a clean `AI_NOT_CONFIGURED` error rather than a crash, validation rejects empty/over-length input, and unauthenticated requests are rejected. This pass also caught and fixed a real bug in `errorHandler.js`: it was overwriting every `ApiError` message at status ≥500 with a generic string, which silently swallowed the intentionally-crafted `AI_NOT_CONFIGURED`/`AI_UPSTREAM_ERROR` text — now only truly unexpected (non-`ApiError`) exceptions get the generic message.
**Update:** `src/services/geminiVoice.js` (the insecure client-side Gemini TTS path) has been deleted — it was fully unused dead code and the single largest security liability in the original audit. `Assistant.jsx` no longer uses the local hardcoded `getAIResponse()` keyword-matcher for open-ended questions; it calls `POST /api/assistant/message` through `AuthContext.authedFetch`, passing the user's current cognitive state and language, and renders the backend's own human-friendly error message (e.g. "AI isn't set up yet") when the gateway is unavailable, rather than silently falling back to canned text. Verified live end-to-end (with no `GEMINI_API_KEY` configured in this dev environment) that the request/response contract between `apiClient.js`'s `ApiError` and the backend's `{error:{code,message}}` shape lines up correctly.
The bKash guided-transaction flow and the screenshot-analysis result in `Assistant.jsx` remain deterministic demo content (not a live AI call) — both are now labeled "(Demo)" in the actual chat text shown to the user, not just in code comments, per the "clearly label simulations" rule. Live screenshot analysis is still Phase 8 work.
**Completion criteria (remaining):** a live `GEMINI_API_KEY` tested against a real model response; RAG/knowledge-grounding layer; response validation/safety filtering layer added before Phase 11 depends on it.

## Phase 8 — Screenshot Understanding
**Dependencies:** Phase 7
**Status: `ScreenshotAnalyzer.jsx`'s upload path is now real end-to-end; `UIExplainer.jsx` intentionally left alone.** `POST /api/screenshots/analyze` (`backend/src/controllers/screenshotController.js`) accepts a multipart upload via `multer` (memory storage only — the file is never written to disk and is discarded once the request completes, per the "don't retain screenshots unnecessarily" rule), validates MIME type (PNG/JPEG/WEBP only) and size (8MB max), then calls `aiGateway.analyzeImage()` with a system prompt asking for strict JSON (safety assessment + up to 8 labeled UI elements, in the user's chosen language) and a defensive parse with a graceful non-JSON fallback rather than a crash.
On the frontend, the previously **completely fake** upload flow — picking any real file always called `runAnalysis('default')` and returned the same canned WhatsApp-shaped result regardless of what was uploaded — is replaced by `runRealAnalysis()`, which actually sends the chosen file via a new `apiFetchForm`/`authedFetchForm` (added to `apiClient.js`/`AuthContext.jsx`) and renders whatever the vision model returns. Verified live (with no `GEMINI_API_KEY` configured in this dev environment): a real PNG upload correctly surfaces the honest `AI_NOT_CONFIGURED` error as a toast instead of silently substituting fake data; wrong file type and missing file are both rejected with clear messages.
The pre-existing per-app canned `ANALYSES` demo buttons stay, but are now explicitly labeled "explore these examples (pre-written, for learning)" rather than implying they're live analysis. `UIExplainer.jsx` (a separate, legitimate static glossary of common app buttons — never claimed to analyze a live screenshot) was left as-is; it isn't dishonest the way the old upload path was.
**Still open:** no `ScreenshotAnalysis`/`VisualExplanation` persistence (each analysis's structured result isn't stored, only a Memory Book summary of it, via the existing `addMemory` call); no visual annotation overlay (numbered markers/arrows drawn directly on the image) — the model's element list is shown as a text list, not superimposed on the screenshot itself; a live `GEMINI_API_KEY` test against a real model response remains untested (this dev environment has none configured).

## Phase 10 — Scam Detection
**Dependencies:** Phase 7
**Status: implemented and tested for URL/SMS/message content.** `backend/src/safety/rules.js` is the deterministic floor: URL analysis (raw-IP links, known shorteners, brand-name-in-domain spoofing e.g. `bkash-verify-now.com`), urgency language, OTP/password/PIN requests, upfront-payment requests, prize/lottery language, and impersonation phrasing, each mapped to a severity and a plain-language reason. `backend/src/services/safetyService.js` combines that floor with an optional AI contextual read through the Phase 7 gateway (`getAiInterpretation`) via `maxSeverity()` — AI can only raise the severity the rules produced, never lower it, and if AI is unavailable the deterministic result alone is still a complete answer (scam detection does not depend on the optional AI feature being configured). Every check is persisted to a new `RiskAssessment` table (content excerpt, severity, matched signals, AI commentary) via `GET/POST /api/safety/analyze` and `GET /api/safety/history`.
Verified live against the README's own canonical example (fake urgent bKash SMS with a spoofed domain) — correctly classifies as `CRITICAL` with three concrete signals; a legitimate `bkash.com` link, an OTP-phishing call script, and a prize-scam message were also verified at the correct tiers, plus validation/auth rejection and CORS from the real frontend origin.
`Safety.jsx` gained a real "Check a Message or Link" tool (`ScamChecker`) at the top of the page calling this endpoint live — type selector (URL/SMS/MESSAGE), a text box, and a result card showing severity, what looks suspicious, what to do, and what to avoid. The pre-existing static `SCAM_EXAMPLES` browsing section below it is kept as explicitly-labeled example/learning content ("Common Scam Examples (for learning)"), not conflated with the live checker.
**Still open:** screenshot submission (the README also lists screenshots as a scam-check input) depends on Phase 8's upload pipeline; the deterministic pattern lists are a useful starting set, not exhaustive — expect false negatives on novel phrasing until broadened.
**Completion criteria:** met for URL/SMS/message; screenshot input remains open pending Phase 8.

## Phase 11 — Psychological Safety Net
**Dependencies:** Phases 3, 10

Wired into `sims/BkashSim.jsx`'s send-money flow, replacing its previous ad hoc inline "Safety Check" box + confirm layout: `handleSend()` now opens the panel instead of a bespoke confirm screen; Proceed continues into the existing guardian-approval demo flow, Edit returns to the form, and Ask for Help shows a reassuring message and returns to the form rather than leaving the user stuck mid-transaction. **Update:** `NagadSim.jsx`'s send-money flow is now also wired to `GuidiaSafetyPanel` (inserted between its recipient/amount form and its OTP-verification step, which stays — Nagad's flow is an OTP-safety lesson, not a duplicate of BkashSim's, so the panel was placed at the point that made sense for its own flow rather than copy-pasted in).

**Completion criteria (remaining):** BkashSim and NagadSim done. GPaySim/PayPalSim blocked on Phase 6 (need a real form first); no account-deletion or permission-grant flow exists yet to wire the panel into either.

## Phase 12 — Guardian
**Dependencies:** Phases 2, 11
**Status: implemented and tested end-to-end, including the full two-account flow.** `GuardianRelationship` and `GuardianApproval` tables back a real invitation → consent → approval-request → resolve workflow: `POST /api/guardians/invite` (senior invites by email, sets an approval threshold, self-invite rejected), `GET /api/guardians` (role-aware: shows relationships where you're the senior, the accepted guardian, or the target of a still-pending invite by email), `POST /api/guardians/:id/accept` (requires the accepting account's own email to match the invite — consent cannot be granted on someone else's behalf), `POST /api/guardians/:id/revoke`, `POST /api/guardians/approvals` (creating a request requires an ACTIVE relationship — a senior cannot request approval from a guardian who hasn't consented), `GET /api/guardians/approvals/mine` (a guardian's own queue), `POST /api/guardians/approvals/:id/resolve` (APPROVED/REJECTED/FLAGGED; only the assigned guardian may resolve; double-resolve rejected).
Verified live with two real registered accounts playing senior and guardian: invite → premature-approval-request correctly blocked (`GUARDIAN_NOT_ACTIVE`) → guardian registers and sees the pending invite by email → accepts → senior requests approval → guardian sees it in their queue → a third party (the senior) is correctly forbidden from resolving it → guardian approves → resolving again correctly rejected → revoke tested.
`GuardianDashboard.jsx` was rebuilt entirely on this real API — removed the previous hardcoded "Karim's Son (Dhaka) — Online" hero card, the fake "Call Now"/"Message" buttons, the hardcoded `ACTIVITY_LOG`, and the fake settings toggles. It now shows: incoming invitations awaiting the current user's consent, an "Invite a Guardian" form (email + approval threshold), the senior's own guardian relationships with live status badges, and — for anyone who is an accepted guardian — a real Approval Requests queue with Approve/Reject/Flag. Also deleted `Guardian.jsx`, a second, entirely disconnected guardian-approval UI prototype that used a different (nonexistent) CSS variable set and was never imported anywhere — dead code from an earlier iteration. Added a "Guardian" entry to the sidebar/topbar navigation, since the dashboard was previously unreachable from any nav link.
**Still open:** approval requests are not yet created automatically from the Safe Practice sims (BkashSim/NagadSim's "guardian approval" step is still a client-side timeout demo, intentionally — see Phase 11's note on why a live cross-account approval can't be meaningfully demoed within a single sim session without a second logged-in guardian). Wiring a sim to call `POST /api/guardians/approvals` for real is a natural follow-up once there's a UI path to select which guardian relationship an approval should go to.
**Completion criteria:** met — consent required at every stage (invite targets an email, only that email can accept, only the accepted guardian can resolve); every value in the dashboard is real, no seed data. Simulated-transaction labeling (no real banking implied) remains enforced at the sim level from Phase 11.

## Phase 14 — Progress and Personalization

**Still open:** no dedicated `ConfidenceProfile`/`SkillProgress` history tables — confidence is a current-value read, not a tracked-over-time profile; per-lesson/per-practice-attempt granularity (vs. the current lesson/safety/interception counts) remains for Phase 5/6 to produce once lesson and practice attempts are themselves persisted server-side.

**Dependencies:** Phases 5, 10, 12, 14
**Status: implemented via synthesis rather than a stored `Notification` table.** `GET /api/notifications` (`backend/src/services/notificationService.js`) builds the feed by querying real events directly — flagged `RiskAssessment`s, new `MemoryBookEntry`s, and resolved `GuardianApproval`s — merged and time-sorted, rather than requiring every feature to remember to write to a separate notifications table. Verified live: the feed exactly reflected the real events accumulated from this session's testing (safety checks, a lesson save, a guardian approval), correctly ordered by time. `AppStateContext` fetches this on login and the hardcoded `NOTIFICATIONS` seed array is deleted; the empty state in `Notifications.jsx` (new) no longer implies notifications always exist.
**Deliberate gap:** read/unread state is **not** persisted server-side (no `POST /:id/read` — synthesized notifications have no row of their own to update). It's tracked client-side in `AppStateContext` for the current session only, so it resets on reload. This is an honest, documented shortcut for this pass, not an oversight — a real implementation would need either a dedicated `Notification` table written by every event source, or a lightweight `NotificationReadState(userId, notificationId)` join table; either is a reasonable follow-up once it's clear whether the product wants read-state to persist across devices/sessions.

## Phase 17 — Security
**Dependencies:** all preceding phases
**Status: substantially already in place incrementally, plus one dedicated pass this session.** Most of this phase's items were actually built alongside each feature rather than retrofitted at the end — every route requires auth via `requireAuth`, every mutation-heavy route (auth, assistant, safety analyze, voice) has its own `express-rate-limit`, every input is zod-validated, ownership is checked on every resource that isn't globally readable (memory entries, guardian approvals — verified via cross-account tests all session), CORS is restricted to `CORS_ORIGIN` (not `*`), and secrets (`GEMINI_API_KEY`, JWT secrets) live only in `backend/.env`, never a `VITE_`-prefixed var — verified by grepping the built frontend bundle, which found none.

## Execution Note
